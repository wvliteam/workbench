## 二、站得住的部分

记下来避免后续改动误伤：

- **契约链完整**：`add` → `lock` 哈希 → `verify` 检出漂移 → `unlock --reason` 强制申报 → `bump` 为消费方自动造返工任务。两个细节说明设计者想清楚了：理由在改动之前落盘（不是改完补），以及内容未变时 `bump` 被拒（防刷版本号）。
- **`selfcheck` 是真的自检**：临时目录跑完整流水线，六十余条断言。
- **规则表驱动**：`GATES` 与 `DEFAULT_ROLE_SCOPES` 是纯数据表，改规则不动逻辑。
- **状态写入原子**：tmp 文件 + `replace`。
- **`read_frozen` 想到了降级路径**：缓存缺失时从 `state.json` 现算，升级前建的项目不会静默退化。

## 三、评审自己判错的地方

这一节是本文存在的主要理由。修好的 bug 在代码里，判错的推理只在这里。

**问题 1 接住了一个没验证过的事实陈述。** 本文引 `architecture.md` 的「`PreToolUse` 载荷里没有『当前是哪个 subagent』…这是上游限制」并接受了它，据此把根因定成上游限制。实测（Claude Code 2.1.252）：subagent 的 `PreToolUse` / `PostToolUse` / `SubagentStop` 载荷都带 `agent_type` 与 `agent_id`，主线程两个都没有；`agent_type` 的值就是 agent 定义 frontmatter 的 `name`，与 `ROLES` 同名。接住对方的理由是对的做法，接住一条未经验证的事实陈述不是。

**给出的备选方案本身也不通。** 本文提的第二条路线是按 `session_id` 分片 role 文件。实测 `session_id` 主线程与 subagent **共享** —— 分片键选错了。本文把这条列在「未验证项」里却同时写成了备选方案，这是最实质的一处方法论失误：未验证的事实不该承重。

**两条路线判成互斥，实际互补。** 本文写「选前者…选后者…」，并据此预告两处落地代价（要给 `requirements.md` 补申报通道、要删 `selfcheck` 里 6 条 role_scopes 断言）。实际两层各管一段：载荷取角色管**当前阶段正在写**的东西（冻结管不了还没定稿的），产物冻结管**已定稿**的上游（冻结不依赖角色，主线程与非角色 agent 也拦得住）。互斥的判断来自那个错的根因。预告的两处代价都没兑现 —— 产物走契约机制自带申报通道，角色取自载荷后 `role_scopes` 不必降级为提示词约定。

**实际付的代价是另一处，实施时才发现。** 产物进 `contracts` 列表后，`contracts_locked` 会从 clarify 一过就永远 PASS，「并行开发前先把接口定下来」这条断言静默作废。靠 `kind: "artifact"` 加一对自检断言解决。**预告代价是对的做法，代价没兑现同样要回写。**

**问题 14 的处方在前置问题修完后失效了。** 处方是「把 `current_task` 纳入冻结清单」。修完问题 3、4 之后没有任何代码读它，冻结一个没有消费者的文件保护不了任何东西 —— 实际做的是删掉它，改冻结 `artifacts.jsonl`（`merge_artifacts` 读它判归属，能追加一行就能把别人的改动记到自己名下）。

**「四条互相咬合必须一起定路线」判得太宽。** 问题 2 与路线无关：`SubagentStop` 改成「只在无 `doing` 任务时清」不需要知道是哪个 subagent 结束了，只需要知道还有没有人在跑。只有问题 3、4 真的必须一起设计。

**「解冻窗口可以拖」的判断被产物冻结推翻。** 当时写的是「窗口仍是单文件，那一条与身份无关，可以等」。产物冻结落地后它变成 `bump` 的必然后果：`bump` 一份产物契约会给每个消费方各建一条同步任务（`artifact-requirements` 的消费方是 `analyst` 与 `architect`），硬规则 5 要求并行派发，两者各要解冻自己那份已冻结产物 —— 后一个 `unlock` 覆盖前一个，前者刚申报完就被拒，理由还是「先申报」。**可接受的误拒和会卡死流程的误拒不是同一件事。** 已改成 `.workbench/unlock/` 目录，见 [architecture.md](architecture.md#解冻窗口按契约分片曾是单文件记录一次纠错)。

**问题 8 的产物一度没有生产者。** 加上 `artifacts: ["verification.md"]` 之后才发现：`>> .workbench/...` 被守卫的 `.workbench` 兜底拦掉，subagent 没有安全的追加通道，而两个开发角色并行时各自 Write 会互相覆盖。定成由编排者复核后写，正好和硬规则 4 对齐 —— 记 subagent 的自述不构成证据。这个约束不在原分析里。
