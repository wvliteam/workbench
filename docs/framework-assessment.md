# 软件开发 Subagents 框架功能设计评估

**评估日期**：2026-09-04

**评估对象**：本仓库当前的软件开发工作台，包括六阶段流程、角色 subagent、任务调度、契约管理、门禁、权限守卫以及 Claude/Codex 适配。`wbsvr` 仅是保留的历史设计文档，服务实现已经移除，不是当前可选能力。

## 一、结论

当前设计方向正确，已经形成一个成熟度较高的**本地研发流程治理内核**，但还不是功能完整的通用 subagents 编排平台。它通过仓库文件、`.workbench`、单一 Python 内核和 hook 工作，不依赖常驻服务、系统账户、sudoers 或安装脚本。

在以下前提下，它是合理且可用的：

- 单个工作区内运行；
- Linux/macOS 等 POSIX 环境；
- 用户或主编排者可信；
- subagent 大体遵守工作台约定；
- 项目团队愿意手工配置门禁命令与角色写入范围。

如果目标是支持不可信 subagent、多个编排者并发、可靠的任务租约、企业级审计和 CI 证明，那么当前本地实现仍缺少一层真正的控制面。主要问题不是六阶段流程缺失，而是**CLI 调用授权、状态一致性、任务所有权和独立验证证据尚未完全内核化**。

## 二、已有能力

### 1. 流程与交接

`clarify → analyze → design → develop → verify → retro` 六阶段、角色、固定产物和门禁集中定义在工作台内核与 skills 中。需求、现状、方案、开发、测试和复盘之间有明确的交接路径，适合重复性研发任务。

### 2. 状态与并发

状态统一落在 `.workbench/state.json`，写入使用排他锁、临时文件和原子替换。PostToolUse 只追加改动流水账，不直接读改 `state.json`，避免并行 agent 用旧快照覆盖任务状态。

### 3. 本地契约与变更传播

契约支持本地 `add`、`lock`、`verify`、`impact`、`unlock`、`bump` 和 `dispute` 生命周期。任务保存 `{name, version, revision, sha}` 快照；契约 bump 会使旧快照任务递归失效，并为消费方创建带新快照的同步任务。设计文档和过门禁的阶段产物也能进入同一套本地冻结机制。

### 4. 权限与安全

PreToolUse 覆盖写出项目根、冻结文件、角色越权写、危险命令和可解析的 Bash 写入路径。Claude 与 Codex 共用本地 hook 内核，Codex 的 `apply_patch` 和 shell 工具也进入同一套目标解析与权限检查。

这套机制保护的是正常工作流中的模型绕过和误操作，不是强对抗安全系统。拥有宿主权限的程序仍可能修改 hook 源码、伪造状态，或通过外部工具短暂修改后还原文件；哈希只能发现当前漂移，不能证明文件中途未被改过。

### 5. 门禁与自检

门禁支持产物存在、章节检查、契约锁定/完整性、任务完成、阻塞检查和外部命令。命令门禁处理超时、零测试和跳过测试标志；`selfcheck` 覆盖状态机、权限守卫、契约漂移、并发写入和任务失效语义。实际行为以 `wb.py` 与 `selfcheck` 为准。

## 三、主要缺口

以下优先级以“subagent 可执行 CLI，且不能完全信任其自报结果”为威胁模型。若整个 CLI 只允许用户执行，P0 项可降为 P1，但不应继续依赖隐含约定。

### P0：CLI 缺少调用者授权与严格状态转移

本地 `config set`、阶段操作和任务操作仍需要明确的调用者矩阵与受保护字段约束。若任意调用者能直接改变阶段、任务图、门禁或契约元数据，便可能伪造完成或绕过流程。

建议：

- 对 `config set` 建立显式可配置字段白名单；
- 将阶段、任务图、门禁记录和契约元数据列为受保护字段；
- 为任务增加 owner、agent_id、lease、attempts 和失败/取消状态；
- 对 `start → doing → done/blocked` 建立严格状态机；
- 对强制推进增加一次性用户授权，而不是只接受 `--force`。

### P0/P1：门禁结果不是独立证明

门禁命令仍在本地执行，编排者同时选择命令、执行命令和判断结果。没有 CI attestation、签名证据或隔离执行时，门禁更像流程约束而不是不可伪造的质量证明；门禁计算与状态提交之间也需要状态 revision 或 compare-and-swap，避免使用过期快照推进阶段。

### P1：任务图和失效传播需要持续验证

任务图需要在设计阶段校验节点唯一性、依赖存在性、无自依赖、无循环、阶段顺序和角色合法性。`blocked` / `stale` 必须递归传播到所有传递下游，包括原先已完成的任务；`done` 与带理由的 `skipped` 才能满足依赖。恢复时只有所有依赖恢复后才允许重新打开任务并刷新契约快照。

同一角色的并行任务仍需要更精确的 agent 归属和任务租约，否则改动归并可能依赖角色与时间窗口。

### P1：门禁默认跳过，项目接入容易漏配

未配置 `gate_commands.test/lint/build` 时命令检查会跳过。文档要求项目自行配置，但初始化没有自动探测测试、构建和 lint，也没有“明确声明无测试”的 waiver。未配置、明确不适用和已通过应当是不同状态。

### P1/P2：数据结构、契约和迁移缺少 schema

状态加载需要 schema version、字段类型校验和可审计迁移。契约主要校验哈希，不校验 OpenAPI/JSON Schema 语法，也不做破坏性变更识别；这些检查应挂到项目门禁，而不是假定哈希能够代替语义校验。

### P2：扩展性、跨端和运维能力有限

阶段、角色和门禁仍集中在 `wb.py` 与多份 prompt 文档中。新增阶段或角色需要同时修改内核、skill、agent 定义和文档，没有项目 profile、插件注册或配置版本管理。

Claude 与 Codex 的宿主工具、模型层级和 hook 信任机制仍不完全等价。项目未受信任或 hook 未加载时，仓库内代码无法自行恢复动态守卫。`fcntl` 不可用时并发保护会降级；完整门禁输出可能包含敏感信息，日志也没有统一脱敏、轮转和保留策略。

## 四、完整性判断

| 能力 | 当前状态 | 判断 |
| --- | --- | --- |
| 六阶段流程 | 已实现，线性推进 | 基础完整，但缺少流程模板和分支流程 |
| 角色职责 | 已实现，Claude/Codex 各有定义 | 职责清楚，跨端存在有损映射 |
| 任务调度 | 已实现依赖前沿和并行批次 | 仍缺少租约、失败状态、循环检测和精确归属 |
| 契约管理 | 本地生命周期、快照、哈希冻结和失效传播 | 仍缺少语法、兼容性和更强的授权控制 |
| 门禁 | 多种断言、日志、超时、零测试与跳过检测 | 未配置命令可跳过，结果缺乏独立证明 |
| 权限守卫 | 工具级和路径级本地检查 | CLI、宿主信任和 bootstrap 模式仍是边界 |
| 托管模式 | `wbsvr` 服务树、系统账户、sudoers 和安装脚本均已移除 | 当前不可用，仅可作为历史设计对比 |
| 可观测性 | 状态、日志、流水账、报告 | 无统一事件 schema、指标、追踪和长期审计留存策略 |
| 可扩展性 | 规则表可修改 | 仍依赖改核心代码和多份 prompt 文档 |
| 跨平台交付 | POSIX/Linux 优先 | Windows 并发安全和 Unix 部署能力不足 |

## 五、推荐演进顺序

1. 明确威胁模型和调用者矩阵，先保护 `config`、阶段、任务图、契约元数据和强推操作。
2. 增加 state schema/version/revision，严格校验状态转移，并用 compare-and-swap 提交门禁结果。
3. 增加任务 owner、agent_id、lease、attempts、失败/取消状态，持续验证递归 stale、循环依赖和 skipped 语义。
4. 为测试、lint、build 和契约检查增加显式 waiver、项目类型探测和 CI 结果接入。
5. 增加迁移机制、项目 profile、统一事件格式、日志脱敏和独立集成测试。
6. 最后再做更多角色、阶段和宿主扩展，避免在控制面不稳定时扩大功能面。

## 六、验证记录

- `python3 .claude/hooks/wb.py status`：当前工作区未初始化，因此没有创建业务 `.workbench`，也未执行流程推进。
- 本次文档修订未运行、也不依赖任何 Go 服务测试；仓库中的 `wbsvr/` 服务树已删除，旧测试结果不能作为当前实现的门禁证据。
- 本评估聚焦当前本地工作流；历史托管设计保留在 [wbsvr.md](wbsvr.md)，不应按当前能力使用。

**最终判断**：框架的流程抽象、契约机制、权限守卫和自检基础都值得保留；下一阶段重点应从增加托管组件转向让本地状态、授权、任务归属和验证证据真正由内核强制。
