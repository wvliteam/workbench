# 知识库（knowledge/）

跨 flow 存活的长期经验库。每条经验一个 markdown 文件，沉淀与查找走 `wb-knowledge` skill 或 `knowledger` 角色。

这里放**换了环境还成立的东西**；只对本次执行成立的留在 `.workbench/artifacts/`，随 flow 归档。判据一句话：

> 换一台机器、下个月再做一次，这条结论还成立吗？

成立的写进来，不成立的不要写。

## 放什么，不放什么

| 长期知识（进这里） | 本次执行（留在 artifacts） |
| --- | --- |
| 实测确认的 runtime 版本约束，含「声明版本不可用、必须用哪个」 | `java -version` 的原始输出与退出码 |
| 正确的构建、启动、测试命令与工作目录 | 本次命令的耗时、时间戳、日志路径 |
| 真实的服务依赖、启动顺序与 readiness 判据 | 本次的 PID、端口占用、临时目录 |
| 每次都会遇到的坑与规避方式（「跑测试前必须先起 docker」） | 本次的一次性网络抖动 |
| 实测推翻文档的结论（写清原记录错在哪里） | 本次的 PASS/FAIL 矩阵与失败诊断过程 |

不放：本次验证通过的结论（验证通过是状态不是知识）、具体凭据值（只记凭据名称与来源位置）、任务进度与计划。

## 条目格式

文件名即主题，kebab-case，英文或中文短语均可（如 `test-needs-docker-first.md`）。正文四个必填章节：

```markdown
# <一句话结论>

## 依据
怎么实测出来的：命令、`file:line`、日期。没有依据的结论不要沉淀。

## 适用范围
对哪个仓库 / 哪个技术栈 / 哪种布局成立。不写「通用」，除非真验证过通用。

## 失效条件
什么情况下这条不再成立（依赖升级、目录改名、流程变更）。写不出来就说明还没想清楚边界。

## 来源
哪条 flow / 哪次复盘沉淀的。
```

## 写入规则

1. **先查重**：沉淀前 grep 现有条目，已有条目优先修订而不是新增。
2. **修订要留痕**：只改被实测推翻或已失效的条目，并在条目里写清原记录错在哪里、新的实测依据是什么。
3. **一条一个结论**：一条经验一个文件，别把整次复盘粘成一个文件。
4. 条目是活文档，**不进契约冻结**；只有本 README（schema 本身）是冻结契约 `knowledge-convention`，改它走 `contract unlock`。

## 查找

```
grep -ril "<关键词>" knowledge/          # 按内容找
ls knowledge/                            # 按主题浏览（目录列表即索引）
```

返回条目时必须带「依据」与「失效条件」—— 只转述结论不给依据的查找结果不可信。没有命中就明说没有，不脑补。

## 与流程的关系

- **retro 出口**：reviewer 在 `retro.md` 沉淀节列出候选清单 → 编排者派 `knowledger` 角色过滤、查重、落盘 → retro 门禁查 `knowledge_written`（有条目，或 retro.md 显式「无可沉淀：<理由>」）。
- **analyze / design 入口**：编排者派发前先查本库，把相关条目连同依据、失效条件注入派发 prompt —— 上次踩过的坑不必再踩一次。
- 独立会话随时可用 `wb-knowledge` skill 沉淀或查找，不必在流水线里。
